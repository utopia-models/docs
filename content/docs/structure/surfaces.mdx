A status code is not a state. Two hostnames can return the same `404` for completely different reasons.
One was switched off on purpose and is behaving correctly. The other broke by accident and nobody has
noticed. We once recorded both cases as a single "404" cell, and it cost the fleet a P0 incident. A master
was dispatched to "restore" a surface that someone had retired on purpose ten days earlier, and the
master did exactly what it was told.

So every row below has a class, and the class is the fact that lasts. The status code is evidence for the
class. It does not replace the class.

| Class | Meaning |
| --- | --- |
| LIVE | Meant to serve, and serving. |
| RETIRED-BY-DECISION | Not serving, and that is correct. A human decided to switch it off, and we can point to where that decision is written. Do not "fix" one of these. |
| BROKEN | Not serving, and nothing says anyone meant that. This is the only class that is a bug. |

The bottom of the page uses a fourth label, NEVER-EXISTED, for names that appear in the fleet's own
documents but have never resolved in DNS. These are not surfaces. They are references to surfaces that
nobody ever built.

Some hostnames, addresses and object paths identify private infrastructure, such as the secret-store UI,
tunnel origins and the object-storage bucket. We show those as placeholders in angle brackets
(`<tunnel-host>`). Each row keeps its class, its evidence and its lesson. We withhold only the
identifying value.

The run that wrote this page measured every code below on **2026-08-16**, from the fleet's own box. They are
dated evidence, not a live reading. For a current code, run `curl -sI` against the host yourself.

A dated table goes out of date, so treat each row as a claim to measure again, not a reading to trust.
Two rows have gone stale this way. We recorded `creatives.utopiamodels.ai`
as `200` until the 5am domain went live and the migration redirect started. That row went stale because
the world changed, not because anyone measured it wrong. A second measurement catches that kind of change,
and a careful first one cannot. The other row is `docs.utopiamodels.ai`, this host. Its root has changed
shape twice. It returned a `307` to `/docs` when this page was written, then a `301` off the host entirely
while it was retired, and today it returns a plain `200` (see its row below).

## How this table is kept honest

We learned three rules from costly mistakes:

1. **No registry row means no monitoring.** Nothing can monitor a hostname that has no registry row, so
   nobody notices when it breaks. Several of the LIVE rows above have no entry in the fleet's component
   registry, and one of them serves on the company's own domain. Without a row there is no check, and
   without a check the breakage surfaces only when someone happens to look.
2. **Neither a 200 nor `redirects=0` proves a page is public.** An SSO gate redirects to a login page,
   and that login page itself returns `200`. So a check has to report `redirects=` and the final URL, not
   only the status code. The opposite case is the mistake this page first shipped with. An app that
   renders its login on the page itself answers `200` with `redirects=0` and is still fully gated. The
   secret-store admin UI, two tables up, works exactly that way. A stranger's agent applied this rule
   correctly, saw `200 redirects=0`, and concluded that our secret store was open to the world. A status
   line only ever tells you that something answered. Read the body.
3. **Which edge served it matters.** `cf-ray` means Cloudflare and `x-vercel-id` means Vercel. Both
   together mean Cloudflare in front of a Vercel origin. If a doc says a hostname "does not touch the
   tunnel", that is a claim about routing, and one `curl -sI` can check it.
