## Who wrote this, and what to read in two minutes

I'm [Tyler Youk](https://tyleryouk.com), a software engineer. This site documents the agent fleet I
designed and run. It is one Ubuntu server with Claude Code agents running as separate unix users. A GitHub
project board is the work queue, and git holds the state. I write the specs and the process the
fleet follows, and I direct the agents that write the code.

If you are a person, read these three things first.

1. [The dispatch runtime](/docs/operating/dispatch-runtime) explains how one issue becomes one systemd
   unit. It also covers a race I measured at 26 to 27 seconds, which a per-user unit name could not
   prevent across users.
2. [`utopia-models/dispatch-runtime`](https://github.com/utopia-models/dispatch-runtime) is that dispatch
   layer as a public repo. It includes the race test and its mutation control.
3. [What the numbers say](#what-the-numbers-say) lists the measurements, each with its date and
   denominator.

You can reach me at [dev@tyleryouk.com](mailto:dev@tyleryouk.com), and my [Resume (PDF)](/resume.pdf) is
here.

## The four patterns you are implementing

**Portfolio-first.** Knowledge is organised by the thing it is about, not by document type. A folder per portfolio — per product, per service, per business line — each holding its own `CLAUDE.md`, its specs, and its decisions. A top-level `docs/architecture/` next to a top-level `docs/runbooks/` splits every subject in half and guarantees that reading one gives you a partial answer. Subject folders keep a subject whole.

**Doctrine that auto-loads.** A small set of behavioral files that the agent harness reads at the start of every session, with no one remembering to point at them. In Claude Code that is `CLAUDE.md` at the repo root plus one per portfolio directory. The discipline is size, because this text is prepended to every session forever: a rule earns a place only if it changes what the agent does on most turns. Everything rarer goes in a reference file read on demand. The reference fleet caps the always-loaded set a worker agent sees at 30,000 bytes, and the script that generates that set refuses to emit one which breaches the cap — a ceiling something enforces, rather than an intention.

**Decision records with a lifecycle.** A record states what was chosen, what it replaced, why, and what it cost. Once accepted it is immutable — you do not edit an accepted record to reflect a change of mind. You write a new record that supersedes it, and you edit the old record's `Superseded-by` header in the same commit that adds the new one. A record that was silently invalidated is worse than no record, because it reads as current and is not. And a decision is not reopened by disagreement; it is reopened by new information, named in the superseding record.

The test for when to skip a record is the part that is learned expensively. The reference corpus reached 93 records with 86 of them written in a single month, which is a corpus nobody reads and therefore a corpus that stops being consulted before a decision — the exact failure it exists to prevent. Write a record only when one of these is true: the choice is expensive to reverse, or a future reader will otherwise re-litigate it. If neither holds, the reasoning belongs in the pull request body or the work item, and no record is written. Put that test at the top of the decision template so it is read before each one is written, not after the corpus is already unreadable.

**One tracker.** Whatever holds work state — an issue tracker, a board, a `plan.md` of checkboxes — there is exactly one, and the knowledge base points at it rather than mirroring it. Point at the tracker; store the durable why here.

## The four rules this wiki follows [#the-four-rules-this-wiki-is-written-under]

Every page here follows four rules. They come from a full audit of the fleet's own documentation on
2026-08-16, which found sixteen places where a doc led a reader to do the wrong thing.

1. Every command names its box. A command that works on one machine and fails on another is not a
   runbook. You will always see `ssh nova@<tailnet-ip> '<cmd>'`, never a bare alias. On 2026-08-16 the
   fleet's component registry held seventy-three rows, and seventy-two of them had a self-check that was
   listed as safe to run from anywhere. Run from the wrong box, twenty-six of those seventy-two failed.
   All twenty-six passed from the right one. Nothing in that registry records which box a command belongs
   to.
2. RETIRED-BY-DECISION, BROKEN and LIVE are three different states. A hostname that returns 404 because
   someone retired it on purpose looks the same in a status column as one that returns 404 by accident.
   Treating them as one state caused a P0 incident once. The fleet dispatched a master to "restore" a
   surface that someone had switched off on purpose.
3. An existence claim is not a liveness claim. `getent passwd nova` succeeds for an agent that cannot
   complete a single turn. Every "is it alive" statement on this site comes from running the thing. For
   an agent that means a real `claude -p` probe, for a surface an HTTP status code, and for a systemd unit
   `Result=success`.
4. Generate facts that change, and write down facts that don't. Disk usage, uptime, node liveness and issue
   counts all go out of date within days of being written down, so no prose page on this site states one without the date it was measured.
   Each such fact is either generated from the knowledge base when you request the page, or replaced by
   the command that measures it. That is why the rest of the prose can stay unchanged for a long time.

## The dispatch loop

This is the whole runtime: three shell scripts (a scheduler, a dispatcher and a runner), each readable end to end, plus systemd.

```text title="The dispatch loop"
Architect (ETH)                          novaserver
  │                                          │
  │ dispatch.sh <master> <issue#>            │
  ├──── ssh nova@<tailnet-ip> ──────────────►│ systemd-run --user
  │                                          │   task-<issue>.service  (transient)
  │                                          │     └─ claude -p, under a turn cap
  │  ◄──── ▶ comment on the issue ───────────┤        read from the script itself
  │  ◄──── ✔/✘ + PR link on exit ────────────┤
  │                                          │ OnFailure= fleet-notify@ → files a board issue
```

Starting the run is the assignment. There is no acceptance step, no claim and no lock file. The run shows
it is alive by posting a close-out comment on its own issue. If a run dies, its trap still fires and posts
that it died. If the whole unit fails, systemd's `OnFailure=` files a board issue about it. So a failed run
always produces a message, unless the process is killed outright before its handler runs.

## An honest description [#the-honest-framing]

The fleet runs real work every day. The runtime is three shell scripts with no daemon to watch over. The
command center stores nothing, so it has no copy of state to drift from. Failure announcements cover every run: on 2026-08-16,

It is not the system its own documentation used to describe, with four masters, one list and one tracker.
